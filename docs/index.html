Background — Key Concepts

What is LLVM? What is LLVM IR? What is MLIR?

Everything you need to understand before looking at the results.

🔧

LLVM — The Compiler Framework

LLVM (Low Level Virtual Machine) is an open-source compiler infrastructure. Clang (C/C++), Rust, Swift, and Julia all use LLVM to convert source code into machine code. It has three stages: Frontend (parse source) → Middle-end (optimize) → Backend (generate x86/ARM code).

📄

LLVM IR — The Intermediate Language

LLVM IR is LLVM's internal "portable assembly." Every instruction is explicit and typed. It's architecture-independent — the optimizer works here before any CPU-specific code is generated.

; x + 0 written in LLVM IR
define i32 @f(i32 %x) {
  %a = add i32 %x, 0
  ret i32 %a
}
🔬

MLIR — Multi-Level IR

MLIR is LLVM's modular sibling (2019). Instead of one IR, it has multiple "dialects" for different abstraction levels. Used by TensorFlow, XLA, and JAX. This project uses the arith.* dialect for integer operations.

🔍

Peephole Optimization

A local rewrite that looks at a small window of instructions and simplifies them. Like replacing x + 0 → x or x XOR x → 0. LLVM's InstCombine pass does these — but it's not exhaustive.

✅

Alive2 — Formal Verification

Alive2 uses SMT (Satisfiability Modulo Theories) solving to mathematically prove that two IR programs are equivalent for ALL possible inputs. If it says valid → correct. If invalid → it gives a concrete counterexample.

🤖

LLM vs LLVM — Key Distinction

LLM (Large Language Model) is an AI (like ChatGPT, Claude). LLVM is a compiler framework. This project asks: can the AI find bugs in the compiler? They have similar names but are completely unrelated technologies.

Methodology

The Experiment Pipeline

Five steps from pattern collection to classification.

1

Collect LLVM IR / MLIR Patterns

53 LLVM IR + 8 MLIR source/candidate pairs. Each file has metadata: EXPECTED, FAMILY, CATEGORY. Includes intentional hallucinations as control cases to test the validator.

2

LLM Proposes Candidate Rewrites

For each source pattern, a candidate *.candidate.ll is provided — a rewrite claiming to be semantically equivalent but simpler or different in form.

3

Formal Validation

LLVM IR: Alive2 (alive-tv) — SMT-based, proves correctness for ALL inputs.
MLIR: Bounded equivalence — both programs evaluated on sampled inputs.

4

Baseline Comparison

Run opt -passes=instcombine,simplifycfg on the source and diff with llvm-diff. If baseline already produces the same output as the candidate → not a "missed" optimization.

5

Classify and Measure

Each case is classified: confirmed_missed, baseline_optimizes, hallucinated, not_missed, or ambiguous. A profitability proxy (instruction count delta) is computed.

Live Examples from the Dataset

Real LLVM IR patterns with their validation outcomes.

✅ Confirmed Missed — bit_extract_alt_form family

The LLM found that shift-then-mask and mask-then-shift are equivalent forms of bitfield extraction. Alive2 proves it. LLVM's instcombine leaves the original unchanged — a genuine gap.

c35_bit_extract_alt_form.llSOURCE
; TITLE: Extract bitfield via mask then shift
; EXPECTED: missed  FAMILY: bit_extract_alt_form

define i32 @f(i32 %x) {
entry:
  ; Step 1: logical shift right by 12
  %a = lshr i32 %x, 12
  ; Step 2: keep low 5 bits (AND 31)
  %b = and  i32 %a, 31
  ret i32 %b
}
c35_bit_extract_alt_form.candidate.llLLM CANDIDATE — Alive2 VALID ✓
; LLM: mask first (bits 12–16), then shift
; 31 << 12 = 126976 = 0x1F000

define i32 @f(i32 %x) {
entry:
  ; Mask target bits in place first
  %m = and  i32 %x, 126976
  ; Then shift down
  %b = lshr i32 %m, 12
  ret i32 %b
}
Why LLVM misses it: InstCombine canonicalizes in one direction only. Both forms are legal IR and produce the same bits — but no rule says "normalize these two forms to each other." This family generalizes across 4 variants (shifts 5, 9, 12, 17; types i32 and i64).
✅ Confirmed Missed — demorgan_complement family (new)

New family added: ~(~x & mask) simplifies to x | ~mask via De Morgan's law. LLVM's instcombine does not fold the XOR-AND-XOR chain into a single OR.

c49_demorgan_complement_mask255_i32.llSOURCE
; TITLE: De Morgan: ~(~x & 0xFF) → x | ~0xFF
; EXPECTED: missed  FAMILY: demorgan_complement

define i32 @f(i32 %x) {
entry:
  ; xor with -1 = bitwise NOT
  %nx = xor i32 %x, -1
  %a  = and i32 %nx, 255
  %r  = xor i32 %a, -1
  ret i32 %r
}
c49_demorgan_complement_mask255_i32.candidate.llLLM CANDIDATE — Alive2 VALID ✓
; De Morgan: ~(~x & 255) = x | ~255
; ~255 = -256 = 0xFFFFFF00

define i32 @f(i32 %x) {
entry:
  ; Single OR replaces 3 instructions
  %r = or i32 %x, -256
  ret i32 %r
}
De Morgan's law: ~(A & B) = ~A | ~B. Substituting A=~x gives ~(~x & mask) = x | ~mask. Three instructions (xor, and, xor) collapse to one (or). LLVM doesn't recognize this cross-instruction chain. Verified on both mask=0xFF and mask=0xF0 variants.
⚡ Already Optimized by LLVM Baseline

LLVM's InstCombine already handles this — the LLM is rediscovering a known optimization, not a missing one. Valid but not a "missed" opportunity.

c01_add_zero.llSOURCE
; TITLE: Remove add by zero
; EXPECTED: already-optimized

define i32 @f(i32 %x) {
entry:
  ; x + 0 is a no-op
  %a = add i32 %x, 0
  ret i32 %a
}
c01_add_zero.candidate.llLLM CANDIDATE — Valid (LLVM already does this)
; LLM: just return x
; opt -passes=instcombine already does this!

define i32 @f(i32 %x) {
entry:
  ret i32 %x
}
Why it's "not missed": Running opt -passes=instcombine on the source already outputs ret i32 %x. The LLM's suggestion is correct but LLVM already knows it. 31 out of 53 LLVM IR cases fell here — the LLM keeps rediscovering solved problems.
👻 Hallucination — boolean arithmetic family

The LLM confused bitwise OR with addition. This looks superficially similar but is mathematically wrong. Alive2 finds a counterexample instantly.

c44_hallucination_or_to_add.llSOURCE
; TITLE: Hallucination: OR rewritten as ADD
; CATEGORY: hallucination
; FAMILY: hallucinated_boolean_arith

define i32 @f(i32 %x, i32 %y) {
entry:
  %a = or i32 %x, %y
  ret i32 %a
}
c44_hallucination_or_to_add.candidate.llHALLUCINATION — Alive2 INVALID ✗
; LLM claims: OR = ADD (WRONG)
; Counterexample: x=1, y=1
;   OR(1,1)  = 1  ← correct
;   ADD(1,1) = 2  ← DIFFERENT!

define i32 @f(i32 %x, i32 %y) {
entry:
  %a = add i32 %x, %y
  ret i32 %a
}
Why the LLM gets this wrong: OR and ADD are identical only when the two values have no overlapping bits. The LLM overgeneralized a conditional identity into an unconditional one. Same mistake repeated for AND→MUL and XOR→SUB. All 4 variants caught by Alive2.
👻 Hallucination — shift semantics family (new)

Two new hallucination types added: confusing arithmetic shift right (sign-extending) with logical shift right (zero-filling), and confusing x*x with x<<x.

c51_hallucination_ashr_to_lshr.llSOURCE
; TITLE: Hallucination: ashr = lshr
; FAMILY: hallucinated_shift_semantics

define i32 @f(i32 %x) {
entry:
  ; arithmetic shift: preserves sign
  %r = ashr i32 %x, 1
  ret i32 %r
}
c51_hallucination_ashr_to_lshr.candidate.llHALLUCINATION — Alive2 INVALID ✗
; LLM: ashr == lshr (WRONG for negatives)
; Counterexample: x = -1
;   ashr(-1, 1) = -1   (0xFFFFFFFF)
;   lshr(-1, 1) = 2147483647 (0x7FFFFFFF)

define i32 @f(i32 %x) {
entry:
  %r = lshr i32 %x, 1
  ret i32 %r
}
ashr vs lshr: ashr fills the vacated bits with the sign bit (1 for negative numbers). lshr always fills with 0. For positive numbers they agree — the LLM saw that pattern and overgeneralized. The second case (c52: x*x = x<<x) fails for x=2: mul gives 4, shl gives 8.
✅ MLIR — Confirmed Missed (mlir_bit_extract_alt_form)

The same bit-extraction pattern exists in MLIR's arith dialect. Bounded equivalence checking over sampled inputs confirms it's valid and MLIR's baseline canonicalization doesn't handle it.

m05_bit_extract_alt_shift3_i32.mlirMLIR SOURCE
// TITLE: MLIR bit extract: shift then mask
// EXPECTED: missed
// FAMILY: mlir_bit_extract_alt_form

module {
  func.func @f(%arg0: i32) -> i32 {
    %c3 = arith.constant 3 : i32
    %0  = arith.shrui %arg0, %c3 : i32
    %c7 = arith.constant 7 : i32
    %1  = arith.andi %0, %c7 : i32
    return %1 : i32
  }
}
m05_bit_extract_alt_shift3_i32.candidate.mlirMLIR CANDIDATE — Bounded VALID ✓
// LLM: mask first (56 = 7<<3), then shift

module {
  func.func @f(%arg0: i32) -> i32 {
    %c56 = arith.constant 56 : i32
    %0   = arith.andi  %arg0, %c56 : i32
    %c3  = arith.constant 3 : i32
    %1   = arith.shrui %0, %c3 : i32
    return %1 : i32
  }
}

Research Question

Can LLMs Discover Useful Missed Optimizations,
or Do They Mostly Hallucinate?

Answer: Both — and formal validation is what makes LLMs useful here

LLMs can discover real, previously-unnoticed optimizations. But they also hallucinate at a measurable rate. The formal verification step (Alive2) is what separates useful suggestions from dangerous ones.

  • LLMs DO find real missed optimizations. 6 of 53 LLVM IR cases (11.3%) and 2 of 8 MLIR cases (25%) are genuine misses. Two distinct families found: bit_extract_alt_form and demorgan_complement.
  • Most suggestions rediscover known things. 31/53 (58.5%) are already in LLVM's instcombine. The LLM is very good at finding obvious identities that are already solved.
  • Hallucination rate is ~11.3% — but 100% were caught by Alive2. Without formal checking, broken rewrites would slip through into production code.
  • Formal verification is non-negotiable. You cannot trust LLM rewrites without a tool like Alive2. The hallucinated shift semantics case (ashr vs lshr) looks plausible but breaks for all negative inputs.
  • Pattern families generalize. When an LLM finds a real optimization, it generalizes across types and constants — evidence of genuine pattern recognition, not random guessing.
  • Best model: LLM as hypothesis generator, Alive2 as filter. Together they form a productive search loop for missed optimizations — neither is useful alone.
